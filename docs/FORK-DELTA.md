# Introduction

This document records what this fork of `ClickHouse/clickhouse-kafka-connect` still patches on top of upstream, and what it gave up in favour of upstream's own implementation when `v1.7.0` was merged in. It is written for whoever runs the next upstream sync: it says which behaviours exist only here, where they live, why upstream does not supply them, and which test or requirement pins each one, so that a merge which silently drops one of them is noticed.

Every row below was checked against the merged and hardened tree on `sync/v1.7.0` (upstream `v1.7.0` merged at `54e63648`, hardened in Phases 13 to 15) that is published as `v1.7.0_gg1` and, after the follow-up hardening of Phases 17 to 19, as `v1.7.0_gg2`, and after the follow-ups of Phases 21 to 23 as `v1.7.0_gg3`, and after the absorption of upstream's untagged tail `a6f1df83` and the discovery fixes of Phases 25 to 28 as `v1.7.0_gg4`, and, with the CI and release-workflow changes of Phases 30 and 31 and no connector source change, as `v1.7.0_gg5`, by searching the code for the construct the row describes. A row that claims a patch survives was only recorded after the patch was found in the source; a row that claims a patch was retired was only recorded after the fork's version was found to be absent. The rows describe what the code contains, not what a plan intended.

Anyone moving a running connector from `v1.7.0_gg4` to `v1.7.0_gg5` should read [`docs/ROLLOUT-v1.7.0_gg5.md`](ROLLOUT-v1.7.0_gg5.md), a one-page note with five measured claims, the first being that no connector code changed. Anyone on an earlier release works through the older notes in turn first: [`docs/ROLLOUT-v1.7.0_gg4.md`](ROLLOUT-v1.7.0_gg4.md), the operator checklist with a self-check per item, for `v1.7.0_gg3`, [`docs/ROLLOUT-v1.7.0_gg3.md`](ROLLOUT-v1.7.0_gg3.md) for `v1.7.0_gg2`, [`docs/ROLLOUT-v1.7.0_gg2.md`](ROLLOUT-v1.7.0_gg2.md) for `v1.7.0_gg1` and [`docs/ROLLOUT-v1.7.0_gg1.md`](ROLLOUT-v1.7.0_gg1.md) for `v1.6.0_gg1`. This file is for the person changing or syncing the code; those are for the person running it.

Two release-identity traps are worth knowing before the next bump. The generated `Version.java` is not an input of `generateVersionFile`, so a `VERSION` edit needs a `clean` build before the generated constant agrees, and the `VERSION` row of the anchor inventory must change in the same commit as the file.
