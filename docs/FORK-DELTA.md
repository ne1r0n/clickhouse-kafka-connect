# Introduction

This document records what this fork of `ClickHouse/clickhouse-kafka-connect` still patches on top of upstream, and what it gave up in favour of upstream's own implementation when `v1.7.0` was merged in. It is written for whoever runs the next upstream sync: it says which behaviours exist only here, where they live, why upstream does not supply them, and which test or requirement pins each one, so that a merge which silently drops one of them is noticed.

Every row below was checked against the merged and hardened tree on `sync/v1.7.0` (upstream `v1.7.0` merged at `54e63648`, hardened in Phases 13 to 15) that is published as `v1.7.0_gg1`, by searching the code for the construct the row describes. A row that claims a patch survives was only recorded after the patch was found in the source; a row that claims a patch was retired was only recorded after the fork's version was found to be absent. The rows describe what the code contains, not what a plan intended.

Anyone moving a running connector from `v1.6.0_gg1` to `v1.7.0_gg1` should work through the operator checklist in [`docs/ROLLOUT-v1.7.0_gg1.md`](ROLLOUT-v1.7.0_gg1.md), which has a self-check per item. This file is for the person changing or syncing the code; that one is for the person running it.

## What this fork still patches

Rows are grouped by area and, inside each group, ordered by file path and then by position in the file. The last column names the requirement ID from the sync milestone, or the numbered Recorded Fact in `.planning/MERGE-CHECKLIST.md` (Facts 1 to 16, the `v1.6.0` sync) or `.planning/MERGE-CHECKLIST-v1.7.0.md` (Facts 17 onward), that pins the behaviour, together with the test classes that exercise it. The facts of the `v1.7.0` sync: upstream `v1.7.0` was merged into `custom_build` on the scratch branch `sync/v1.7.0` as one mechanical merge commit, `54e63648`; the rollback tag `pre-v1.7.0-sync` marks the `custom_build` tip before the merge (`c61d90ce`); the release is `v1.7.0_gg1`. The most expensive fact of the `v1.6.0` sync is that seven fork behaviours vanished from the merge with no conflict marker and no compile error. The one found last, the test harness's default ClickHouse image reverting from `latest` to a pinned version, was found only after two phases had closed green against the wrong server. That is why every one of them now has a test pinning it, and why a green build after a merge is not evidence that the fork's behaviour survived: check each row of [What this fork still patches](#what-this-fork-still-patches) against the new tree.

An eighth behaviour was easy to lose the same way, because it was one line in a helper with no failing test on any server older than ClickHouse 26.9: the forced `network_compression_method=lz4`. Since the v1.7.0 sync it is retired onto upstream's `setCompressionMethod` flag (see the row under [Retired in favour of an upstream implementation](#retired-in-favour-of-an-upstream-implementation)), so an upstream sync no longer has to carry it. The hazard that remains is an operator one: `compress=true` in `jdbcConnectionProperties` re-enables response compression on client V2, and combined with `setCompressionMethod=false` against a 26.9+ server it fails reads with the LZ4 magic-byte error.

Two release-identity traps are worth knowing before the next bump. The generated `Version.java` is not an input of `generateVersionFile`, so a `VERSION` edit needs a `clean` build before the generated constant agrees, and the `VERSION` row of the anchor inventory must change in the same commit as the file. And the CI trigger is branch-only on purpose (see the CI row): a tag pushed onto an already-pushed SHA used to cancel the branch run.

The mechanical checks are `.planning/scripts/verify-merge-invariants.sh` with its anchor inventory `.planning/scripts/fork-anchors.txt`, run at the end of every phase from 12 to 15. An anchor that moves must move in the commit that moves the code, so a merge that silently drops a fork behaviour fails the script instead of passing a green build.
