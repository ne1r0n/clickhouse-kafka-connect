# Rollout checklist: `v1.7.0_gg7` to `v1.7.0_gg8`

**The connector source changes in this release.** `git diff --shortstat v1.7.0_gg7 v1.7.0_gg8 -- src/main` reports 6 files changed, 428 insertions and 72 deletions. It was measured with `HEAD` in place of `v1.7.0_gg8` on the release tip, because the tag `v1.7.0_gg8` does not exist before the release is published, and so was every other command of this note that names `v1.7.0_gg8`. The five changes at a glance:

1. Two items of upstream's untagged tail are new: a serialization failure now logs one ERROR line with its record context and no record value, and a field name that contains `/` in a `DESCRIBE` response is pinned by tests (section A).
2. The insert timeout `clickhouseClientInsertTimeoutMs` now bounds more on both clients: on client V2 a body-write stall, on client V1 the wait for the insert response. Both end with a retriable error, and a timed-out insert can produce a duplicate (section B).
3. `ClickHouseSinkTask.stop()` stops the proxy task even when the delivery strategy's `stop()` throws; a `RetriableException` out of `put` is redelivered without bound, a limit by decision; and the retry-budget question for `additionalRetriableErrorCodes` is closed by decision (section C).
4. The public constant `DeclaredNullability.ESCAPED_NEWLINE` is removed from the connector jar (section D).
5. The release identity, which the JMX name and the client name carry, reads `v1.7.0_gg8`; the archive differs from the `v1.7.0_gg7` archive in connector classes and the manifest only; and the rollback is rehearsed (section E).

The fork's own changes are listed in [`../CHANGELOG.md`](../CHANGELOG.md), and [`FORK-DELTA.md`](FORK-DELTA.md) lists everything the fork patches on top of upstream. If you are coming from a release before `v1.7.0_gg7`, work through [`ROLLOUT-v1.7.0_gg7.md`](ROLLOUT-v1.7.0_gg7.md) first and return here afterwards.

This note names no host, connector, cluster or production system. Every environment-specific value is an angle-bracket value, such as `<connector-name>`, `<topic>`, `<group>` or `<dir>`; replace each one with your own value.

**How each claim is labelled.** Every effect of this release has one row in a table below, with a label for how the claim is known. There are three labels:

- `measured`: a test or a command ran, and the row names it.
- `read from the code`: the row names a file and a site; nothing ran for this claim.
- `derived`: the claim follows from other rows or from a stated mechanism; nothing ran for this claim itself.

A label may carry one parenthetical qualifier that narrows it, for example `measured (stub only)`. A row that makes claims of different strength says which label each claim has, in the form `claim: label; claim: label`.

**Which connectors a row concerns.** The column `Applies when` limits each row. A connector runs client V2 only when its configuration sets `client_version` to a value other than `V1`; a connector that does not set `client_version` runs client V1, the default (read from the code: `ClickHouseSinkConfig` reads `client_version` with the default `V1`, and `ClickHouseWriter` selects client V2 for any other value). Every statement that holds only on client V2 says `client V2`, and every statement that holds only on client V1 says `client V1`. The values are:

- `client V2`, `client V1`, `client V1 and client V2` and `either client`: the row holds on that client, or on both. A setting after a comma, for example `client V2, socket_timeout not set by the operator`, adds a setting the row needs.
- `any connector with a dead letter queue`, `any connector that sets additionalRetriableErrorCodes` and `anyone compiling against the connector jar`: the row concerns exactly that configuration or that reader.
- `this release`: the row describes the release as a whole. `CI only`: the row concerns the build and test workflows, not the archive. `as named in the row`: the row names its cases itself.

## Before you upgrade

Work through these steps before you roll the new archive out. Each names the section it comes from.

1. On every connector, compare the longest insert time you see against `clickhouseClientInsertTimeoutMs` (default four minutes), and decide whether to raise it or to name `socket_timeout` in `jdbcConnectionProperties` (section B). A client V2 batch is now cut if its body is still being sent at the bound, serialization included.
2. A connector that runs client V1, which is every connector without `client_version`, now has a connector-side insert bound: an insert still waiting for its response at the bound, including one whose server keeps streaming progress headers, fails and is redelivered (section B). At the default a quiet client V1 insert still ends at the library's own 30 s limit.
3. With `exactlyOnce=false`, a duplicate is possible after an insert that timed out and that the server committed anyway, in a table that does not deduplicate the repeat (section B).
4. A parser or an alert that reads the topic, the partition, the offset or the column out of an exception message needs the ERROR line `Record serialization failed` instead (section A); the same ERROR lines also appear on a deadline cut, and neither means the record is bad (section B).
5. A failure that carries a `RetriableException` is redelivered without bound under both `errors.tolerance` values; there is no retry budget and no setting to add one (section C).
6. Anything compiled against `DeclaredNullability.ESCAPED_NEWLINE` needs its own copy of the constant (section D).
7. Update dashboard, alert and exporter matchers that spell out `version=v1.7.0_gg7` or `clickhouse-kafka-connect/v1.7.0_gg7` (section E).

## B. Insert timeout limits

This section concerns the insert limit `clickhouseClientInsertTimeoutMs` on both clients, and the two clients are bounded by different mechanisms. A connector that does not set `client_version` runs client V1, the default, and the rows that say client V1 are the ones that reach it; on client V2 the bounds are a read-inactivity limit and a write-phase deadline. `async=false` is the client V2 default (read from the code: the comment on `ClickHouseWriter.awaitInsertResponse`), and `socket_timeout` is the client option that an operator names in `jdbcConnectionProperties`; the ClickHouse `async_insert` setting is a different thing and the connector does not touch it.

What to do:

1. Compare the longest insert you see against `clickhouseClientInsertTimeoutMs` on both clients now: a client V2 batch is cut if its body, serialization included, is still being sent at the bound, and a client V1 insert is cut if it is still waiting for its response at the bound (rows T2 and T3). For a legitimately slow insert, raise `clickhouseClientInsertTimeoutMs`, or name `socket_timeout` in `jdbcConnectionProperties`, which removes the connector's bounds (row T5).
2. With `exactlyOnce=false`, expect a possible duplicate after an insert that timed out and that the server committed anyway, unless the table deduplicates the repeat. With `exactlyOnce=true` the retry reuses its deduplication token (row T8).
3. Do not read the bound as a cap on the total insert time, or as covering a client V2 insert whose body has been sent while the server streams progress headers, or a request that is not an insert (rows T6 and T7).
4. If an alert matches the two ERROR lines of row T10, expect them on a deadline cut too; they do not mean the record is bad.

### Rollback

This release changes no state format and no table format (`KeeperStateProvider` and `Processing` have no change since `v1.7.0_gg7`), so a rollback is a code rollback. Tag `pre-v1.7.0_gg8` names commit `94834763`, the published tip of `custom_build` before this release, which is also tag `v1.7.0_gg7`. The tag is created locally before the release and pushed to origin when the release is published. Step 2 needs it on origin: if `git fetch --tags origin` does not bring `pre-v1.7.0_gg8`, stop and ask the maintainer to publish it.

1. Start from the published tip with nothing uncommitted. Run `git fetch --tags origin`, `git checkout custom_build` and `git merge --ff-only origin/custom_build`, and check that `git status --porcelain` prints nothing. Set whatever it lists aside with `git stash -u`, keep it on its own branch, or work in a fresh clone, so that none of it becomes part of the rollback; do not commit it on `custom_build`, because step 2 branches from there and step 4 publishes that branch: the `git read-tree` of step 2 discards uncommitted and staged changes to tracked files without asking, and it overwrites untracked files at paths that the tag contains.
2. Restore the tree of the tag in one commit on a new branch, so that your local `custom_build` stays as published. This commit is `<rollback-commit>`:

```sh
git switch -c rollback-v1.7.0_gg8
git read-tree -u --reset pre-v1.7.0_gg8
git commit -m "Roll back v1.7.0_gg8"
git diff --quiet HEAD pre-v1.7.0_gg8 && echo ok
```

## Known limits carried into this release

These limits exist in this release; none is fixed here. Each bullet points at its rows.

- The closing of helper clients has residuals: a Keeper state provider constructor that fails on client V1, a helper-client constructor that fails after it built its client V2 instance, a second `start()` on one writer, and a five-second wait that can end with a table refresh still running on a closed client. Two stop limits are new: when both the delivery strategy's `stop()` and the proxy stop throw, the strategy's exception is dropped, and a throw from the partition removal that `close(partitions)` runs first skips the delivery strategy's `close` (row S2).
- The bounded insert has limits: a client V2 insert whose body has been sent while the server streams progress headers is not bounded (measured), a request that is not an insert is not bounded, and a timed-out insert is not rolled back (rows T6, T7 and T8).
- A many-to-one rename and a partition-changing SMT are not supported for exactly-once, the in-memory state machine or `reportInsertedOffsets`; this is carried unchanged from row R3 of the `v1.7.0_gg7` note, together with its limits under other topic-changing SMTs, and this release does not change it.
- A `RetriableException` out of `put` is redelivered without bound under both `errors.tolerance` values, and a code in `additionalRetriableErrorCodes` is redelivered the same way; both are limits by decision (rows S3 and S4).
- Carried from the `v1.7.0_gg6` note as information, as the `v1.7.0_gg7` note carried it: that note does not state what a first chunk with exactly the stored range does after the upgrade (the `SAME` state of `Processing.doLogic`), and its section B lists configurations it does not characterise. `Processing.doLogic` is unchanged since `v1.7.0_gg7`, and this note adds no statement about either.
