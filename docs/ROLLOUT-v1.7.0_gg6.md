# Rollout checklist: `v1.7.0_gg5` to `v1.7.0_gg6`

**The connector source changes in this release.** The previous release changed no connector code; this one does. `git diff --shortstat v1.7.0_gg5 HEAD -- src/main` on the release tip reports 7 files changed, 112 insertions and 31 deletions: the buffer strategies and `ChunkFlusher`, `ClickHouseSinkConfig`, `ProxySinkTask`, `Utils` and `ClickHouseHelperClient`. The five changes at a glance:

1. A buffered connector (`bufferCount > 0`) under a topic-changing SMT now commits offsets under the original topic and partition (section B).
2. The ClickHouse Java client moves to `0.11.0`, with one item that breaks an upgrade on client V2: `custom_` keys in `jdbcConnectionProperties` (section D).
3. A new setting, `additionalRetriableErrorCodes` (section C).
4. Dependency changes, among them a security release of `lz4-java` (section E).
5. The release identity, which the JMX name and the client name carry, reads `v1.7.0_gg6` (section E).

The fork's own changes are listed in [`../CHANGELOG.md`](../CHANGELOG.md), and [`FORK-DELTA.md`](FORK-DELTA.md) lists everything the fork patches on top of upstream. If you are coming from a release before `v1.7.0_gg5`, work through [`ROLLOUT-v1.7.0_gg5.md`](ROLLOUT-v1.7.0_gg5.md) first and return here afterwards.

This note names no host, connector, cluster or production system. Every environment-specific value is an angle-bracket value, such as `<connector-name>`, `<bootstrap>`, `<group>`, `<topic>` or `<dir>`; replace each one with your own value.

**How each claim is labelled.** Every effect of this release has one row in a table below, with a label for how the claim is known. There are four labels:

- `measured`: a command or a test ran, and the row names it.
- `read from the code`: the row names a file and a site; nothing was run.
- `derived from Kafka consumer-group semantics (not measured)`: the claim follows from how Kafka and Kafka Connect define the behaviour; no broker and no Connect worker ran for it.
- `measured in research (not re-run)`: the maintainers measured it while preparing the release, on throwaway clones and in the public `confluentinc/cp-kafka-connect-base:7.9.7` image, and did not repeat it on the release tip.

A row that makes claims of different strength says which label each claim has. The column `Applies when` reads `either client` (the row holds on client library `0.9.6` and on `0.11.0`; it does not say client V1 or client V2), `client 0.11.0 ships` (the row exists because the client moves to `0.11.0`), `client V1 insert path` (the row holds only on the client V1 insert methods of the connector) or `this release`.

## Before you upgrade

Work through these six steps before you roll the new archive out. Each names the rows it comes from.

1. Search every connector's `jdbcConnectionProperties` for keys that start with `custom_`, for `decompress=true`, and for any expectation that `ssl` or `sslmode` there changes the transport (rows D1, D7, D8). On client V2 (`client_version` set to a value other than `V1`), `ssl` and `sslmode` never changed the transport, and a `custom_` key makes the task fail after the upgrade (row D7). A connector runs client V1 when it does not set `client_version`: there `ssl` and `sslmode` are read from the connection URL and must stay (read from the code: `ClickHouseHelperClient.createClientV1`; what the V1 artifacts of `0.11.0` do with them was not audited), and `custom_` keys are not affected (row D7).
2. For a connector with `bufferCount > 0` and a topic-changing SMT, describe its consumer group and decide where the first start should resume (rows B3, B4).
3. Check that the Connect runtime has the three `SinkRecord` original-topic accessors; the `javap` command is in the section "Minimum Connect runtime" (row B6).
4. Check the platform and the temp folder of a worker that may take the ZSTD path (row D9).
5. On client V2, review `retryOnSocketException`, proxy rules that match the `User-Agent`, and log alerts that match the old texts (rows D3, D5, D6, which were measured or read for client V2; client V1 was not audited for them). On any client, review a filter or alert on the unmapped-key WARN (row D6), which also reaches client V1 connectors.
6. Update dashboard, alert and exporter matchers that spell out `version=v1.7.0_gg5` or `clickhouse-kafka-connect/v1.7.0_gg5` (row E3).

A connector that sets `additionalRetriableErrorCodes` lists only transient codes (row C2).

## B. Buffered connectors under topic-renaming SMTs

An unbuffered connector has `bufferCount` at its default of 0, and its delivery path is called the Direct path in this note (read from the code: `ClickHouseSinkTask.createDeliveryStrategy` chooses `DirectDeliveryStrategy` exactly when `bufferCount` is not above 0, and a buffer strategy otherwise). The fix of this release is in the buffer strategies, so it does not reach the Direct path; row B8 states what that means under a rename.

### What changes

With `bufferCount > 0` and an SMT that changes the record's topic, earlier releases returned offsets keyed by the renamed topic from `preCommit` (row B1). Kafka Connect accepts an offset only for a partition the consumer was assigned, so nothing was committed for the group (row B2). This release returns the original topic and partition at the last flushed offset plus one, so after a restart or a rebalance the group resumes from the last flushed offset instead of rereading from where `auto.offset.reset` points.

The edit is small and sits in three buffer files (`ChunkFlusher`, `AtLeastOnceBufferStrategy`, `ExactlyOnceBufferStrategy`). `Processing.java`, the state key, the KeeperMap row schema and the `BEFORE` and `AFTER` flag sequence are untouched (read from the code: the diff of those files since `v1.7.0_gg5` is empty). The fix is fork-only (row B7).

Affected: connectors with `bufferCount > 0`, with at-least-once or exactly-once buffering, and an SMT that changes the topic. Not changed by this release: unbuffered connectors (`bufferCount` 0, the Direct path), buffered connectors without renamed topics, and the `bufferCount` and `bufferFlushTime` contract (row B5). One limit stays on the unbuffered path: with `reportInsertedOffsets=true` under a topic-changing SMT it commits nothing, and this release does not change that path (read from the code: its files are unchanged since `v1.7.0_gg5`; row B8).

### First start after the upgrade

Every claim in this subsection carries the label `derived from Kafka consumer-group semantics (not measured)` in its row (B3, B4); no broker and no Connect worker ran for it.

The previous archive never advanced the group's committed offset for these partitions. The first start on the new archive therefore resumes exactly where a restart of the previous archive would have: at the group's existing committed offset if one exists (for example one left from a period before `bufferCount` was turned on), otherwise at the position `auto.offset.reset` selects.

Connect's default `auto.offset.reset` for sink consumers is not verified here, so check the worker's `consumer.auto.offset.reset` and any connector-level `consumer.override.auto.offset.reset` before relying on it. With `earliest` and no committed offset, the connector rereads the retained topic from its beginning once; the upgrade restarts the connector, so that one reread coincides with the upgrade. From the first successful flush on, the group's offsets advance and later restarts and rebalances no longer reread.

A group that stays without commits can lose even a stale committed offset once it has been empty for longer than the broker's `offsets.retention.minutes`; check that setting on your brokers (row B4).

### What to do

1. Before the upgrade, run a read-only check against your own cluster. Describe the group; `<group>` is `connect-<connector-name>` unless the connector overrides the group id:

   ```sh
   kafka-consumer-groups --bootstrap-server <bootstrap> --describe --group <group>
   ```

   The output shows whether committed offsets exist and where they are.

2. Decide where the first start should resume. Either accept one reread, when the table deduplicates or the load is idempotent, or stop the connector and set the group's offsets to the position you want before starting the new archive, with `kafka-consumer-groups --bootstrap-server <bootstrap> --group <group> --topic <topic> --reset-offsets <position option> --execute`. Choose a position at or before the last record already in the table: a later position skips records for good, and an earlier one reloads them (derived from Kafka consumer-group semantics (not measured)). The offset reset changes live state: try it first on a group that no live pipeline uses, and verify the options against your Kafka version.
3. After the first successful flush, run the describe command again and confirm that the committed offsets advance.

### Minimum Connect runtime

The fix calls `SinkRecord.originalTopic()`, `originalKafkaPartition()` and `originalKafkaOffset()` (row B6). All three are present in `connect-api` 4.1.1 and 4.4.0 (measured with `javap`, re-run for this note) and in the `connect-api` jar of the `confluentinc/cp-kafka-connect-base:7.9.7` worker image (measured in research, not re-run), and the connector's Kafka API list is guarded by `ConnectApiReferencesUnitTest`. A Connect runtime without them fails with `NoSuchMethodError`, and the two failure modes are read from the code:

- Exactly-once: `ExactlyOnceBufferStrategy.put` calls `originalTopic()` before any insert, so the first `put` fails.
- At-least-once: `ChunkFlusher.flush` inserts the chunk first and reaches the new accessors only afterwards. `NoSuchMethodError` is an `Error`, and `AtLeastOnceBufferStrategy.put` catches only `RuntimeException`, so the inserted chunk stays buffered with no offset recorded and is redelivered as a duplicate.

The oldest runtime that has them was not measured, and nothing here ran an older runtime. The text of upstream pull request 786, which targets the same defect, says Kafka Connect 3.6 and later; that figure is taken from the text of the pull request and was not verified here. To check your own runtime, run `javap -cp <connect-api jar> org.apache.kafka.connect.sink.SinkRecord` and look for `originalTopic`, `originalKafkaPartition` and `originalKafkaOffset`; a runtime that lacks one of them is affected.

### What the setting does

`additionalRetriableErrorCodes` takes a comma-separated list of ClickHouse server error codes, for example `additionalRetriableErrorCodes=<code>,<code>`. It defaults to empty; with it unset the connector behaves as before. The parse rules are those of row C1. The built-in set of 15 codes, 159 (`TIMEOUT_EXCEEDED`) among them, stays in force, and the setting adds to it; it does not change the ClickHouse Java client's own retry settings.

### The bypass of errors.tolerance

A code in the list makes the connector throw `RetriableException`, and Kafka Connect then redelivers the same batch. That redelivery has no retry budget and does not go through `errors.tolerance` or the dead letter queue (row C2). A code that is not transient therefore makes the task loop on the same batch: list only codes that are transient, such as an overloaded server or a table that is briefly read-only.

### Two retriable behaviours that no test asserts

Row C3 names two cases that are retriable today although no test asserts them. A decision on changing either is open; this release leaves both as they are.

## D. ClickHouse Java client 0.11.0

The connector's ClickHouse Java client moves from `0.9.6` to `0.11.0`. The connector keeps working on the new client, and one effect breaks an upgrade for a connector on client V2 that sets `custom_` keys in `jdbcConnectionProperties` (row D7). A row says in `Applies when` whether it holds on both client lines or only because the client moves.

- Which client a connector runs decides which rows describe it. A connector runs client V2 only when its configuration sets `client_version` to a value other than `V1`; without `client_version` it runs client V1 (read from the code: `ClickHouseSinkConfig` and `ClickHouseWriter.start`).
- Rows D1 to D8, D10 and D11 were measured or read for client V2 and are not a statement about client V1, with one exception that reaches both: every connector builds a client V2 object when it starts and, on client V1, again for every insert, from `jdbcConnectionProperties`, whatever `client_version` says (read from the code: the `ClickHouseHelperClient` constructor creates both clients, `createClientV2` and `createClientV1`, and `ClickHouseWriter.getMutationRequest`, which each of the three client V1 insert methods (RowBinary, JSON and String) calls, builds a new `ClickHouseHelperClient` to read its node).
- The `ignore_unknown_config_key` default and the WARN of row D1 therefore apply to client V1 connectors as well, and a client V1 connector that carries `ssl` or `sslmode` logs that WARN once for every insert batch, not only at start (the WARN is raised when the object is built, read from the public `client-v2` 0.11.0 sources: `Client` constructor, `ClientConfigProperties.parseConfigMap`).
- That WARN is not new with this release: the `v1.7.0_gg5` tree already built the object for every client V1 insert and passed it every `jdbcConnectionProperties` pair, and client `0.9.6` already logged a WARN for a key it does not map, at the same place, so a client V1 connector that carries `ssl` or `sslmode` already logged one such WARN per insert batch on `v1.7.0_gg5`. Only the text changes: `0.9.6` prints the remaining keys with their values as a map, and `0.11.0` prints the key names, as in `Unknown and unmapped config properties: [ssl, sslmode]` (read from the code: `ClickHouseHelperClient.createClientV2` and `ClickHouseWriter.getMutationRequest` of tag `v1.7.0_gg5`, and the bytecode of `ClientConfigProperties.parseConfigMap` and of the `Client` constructor in the public `client-v2` 0.9.6 and 0.11.0 jars, read with `javap`; the `0.9.6` half was not run).
- Those objects send no request on client V1, because the connector uses them only behind the client V2 switch (read from the code: the V2 methods of `ClickHouseHelperClient`, the V2 insert methods of `ClickHouseWriter` and the V2 branches of `KeeperStateProvider`); that is why `custom_` keys are not a problem for client V1 (row D7).
- Rows D9 and D12 concern the archive that both clients ship in. Row D13 states a client V1 half and a client V2 half, and each holds on its own client. Row D14 concerns the client V1 insert path: the connector creates the piped streams behind it only in its client V1 insert methods and its client V2 insert methods create none (read from the code: `ClickHouseWriter`), so the row is not a statement about client V2. What the move to `0.11.0` changes in the V1 library artifacts (`clickhouse-client`, `clickhouse-http-client` and `clickhouse-data`, which share the version with the V2 client) was not audited beyond rows D13 and D14 and one V1-mode run of the live tests in the maintainers' research (35 tests, no failure; `measured in research (not re-run)`).

### `custom_` keys in `jdbcConnectionProperties` (this breaks an upgrade on client V2)

Client 0.11.0 forwards every `jdbcConnectionProperties` key that starts with `custom_` to the server as a query parameter on V2 requests, and it percent-encodes the operator's value a second time. Client 0.9.6 ignored these keys. A stub-server probe of the maintainers builds a V2 client with `?custom_settings=max_threads%3D3&custom_myparam=7&ssl=true` and prints the request line of the insert. Measured in research on both client lines, not repeated on the release tip (the operator's `%3D` becomes `%253D` on 0.11.0):

```text
0.11.0: /?custom_myparam=7&custom_settings=max_threads%253D3&query=INSERT%20INTO%20t%20FORMAT%20RowBinary&network_compression_method=lz4
0.9.6:  /?query=INSERT%20INTO%20t%20FORMAT%20RowBinary&network_compression_method=lz4
```

A real server rejects the forwarded parameter. Measured by sending `SELECT 1` with a `custom_myparam=7` parameter over HTTP to a throwaway ClickHouse 26.10.3.7 container (the request did not go through the connector); the answer was:

```text
Code: 115. DB::Exception: Setting custom_myparam is neither a builtin setting nor started with the prefix 'SQL_' registered for user-defined settings. (UNKNOWN_SETTING) (version 26.10.3.7 (official build))
```

A client V2 connector sends the key with every request, its start-up ping included, so the task does not start. Measured on the release tip against a throwaway ClickHouse 26.10.3.7 container (see the How cell of row D7): `ClickHouseSinkTask.start` threw `Connection to ClickHouse is not active.` with `errors.tolerance=none` and with `errors.tolerance=all`. `errors.tolerance` does not change that, because `start` runs before any record is delivered. The log shows `Unable to ping ClickHouse instance.` and `Unable to ping Clickhouse server.` at ERROR; the code 115 text appeared only with the client's logger at DEBUG. The path is read from the code: `Client.ping`, `ClickHouseWriter.start` and `ProxySinkTask.start`. The symptom is a task that fails at start, not rows that go missing.

What to search for: `custom_` in every `jdbcConnectionProperties` value of every connector, before moving. A connector runs client V2 only when its configuration sets `client_version` to a value other than `V1`; without `client_version` it runs client V1 (read from the code: `ClickHouseSinkConfig` and `ClickHouseWriter.start`). On client V1, `custom_settings` is the client's own option and keeps working, so keep it there; the search also finds V1 connectors, which need no change for this item. On client V2 the remedy is to remove or rename the key. The connector has no switch that restores the old behaviour in this release.

### zstd-jni: platforms and the temp folder

Each fact carries the label of row D9.

- The `cloud` jar that client 0.11.0 declares carries three natives, `darwin/aarch64`, `linux/aarch64` and `linux/amd64` (measured: the archive compare lists exactly those three as new).
- The plain `zstd-jni` jar carries more platforms, among them linux arm, i386, loongarch64, mips64, ppc64, ppc64le, riscv64 and s390x, windows aarch64, amd64 and x86, freebsd, aix and darwin x86_64 (Intel macOS); the `cloud` jar carries none of them (measured in research, not re-run).
- On an unsupported platform the load throws `UnsatisfiedLinkError: Unsupported OS/arch, cannot find /<os>/<arch>/libzstd-jni-1.5.7-23.<ext>`. The library has no pure-Java fallback (read from the code).
- With `/tmp` mounted `noexec` the failure reads `failed to map segment from shared object`. Two remedies work: `-DZstdTempFolder=<dir>` or `-Djava.io.tmpdir=<dir>`, with `<dir>` an executable folder (measured in research, not re-run).
- `ZstdNativePath` is a third system property. It loads the given file and has no fallback (read from the code).
- An `Error`, not an exception, escapes the failing load. `Utils.getRootCause` returns null for it, so the task fails without a retry (read from the code).
- The default configuration never reaches the ZSTD path: the connector's `setCompressionMethod` true with `compress=false`, or with `compress=true`, mapped no zstd native in the maintainers' probe (measured in research, not re-run). On client V2, a connector reaches it only with `compress=true` together with `setCompressionMethod=false`, or with `decompress=true`. On client V1 that condition was not verified: the V1 artifacts of `0.11.0` contain a ZSTD route of their own behind the options `compress_algorithm` and `decompress_algorithm` (read from the code, not run: `ClickHouseClientOption` in `clickhouse-client`, and in `clickhouse-data` `ClickHouseCompressionAlgorithm.of` maps ZSTD to `ZstdSupport.getInstance()`, whose `DefaultImpl` uses the `com.github.luben.zstd` classes, read with `javap`; the same classes exist in `0.9.6`, whose archive did not ship `zstd-jni`). The connector sets neither option itself, and whether a `jdbcConnectionProperties` value reaches that route, and whether the native then loads, was not run, so a client V1 connector that sets either option is covered by the platform and temp-folder checks of row D9 until shown otherwise.
- Alpine and other musl workers were not tested.

### A batch replayed across the upgrade (the clean-stop requirement)

For a connector on client V2: a `BEFORE_PROCESSING` batch that is replayed after the upgrade is rebuilt by the new task from the stored offset range. The same writer serialises it into the same bytes, and the same path sends it with the same body and the same `insert_deduplication_token`, so ClickHouse's block deduplication sees the block the old task would have sent. The `User-Agent` header is the only request header that differs (row D11).

- The golden (measured): 96 RowBinary bodies, 48 type cases in two variants, blessed on client 0.9.6 and green on 0.11.0. It compares the serialiser's bytes, which the test's own comment says do not depend on the client.
- The wire pin (measured): `ClientInsertWirePinUnitTest`, which builds its client with `useClientV2(true)`, shows a 100,000-byte body, the token and no `Content-Encoding` arriving unchanged on 0.11.0.
- The token (read from the code): `QueryIdentifier.getDeduplicationToken` builds `topic-partition-minOffset-maxOffset` from the batch, not from the client.

On client V2, no clean stop is required, for the compared matrix only. The scope is the 48 type cases in both variants: a column type outside the matrix, a time-zoned `DateTime` and a `Variant` fed plain text were not compared.

A connector on client V1, which a connector runs when it does not set `client_version`, is not covered by the wire pin: no test compares the body or the `insert_deduplication_token` that a client V1 insert sends, and the V1 artifacts of `0.11.0` are the part that section D says was not audited. Read from the code: `doInsertRawBinaryV1` calls the same `writeRecordsRowBinary` as the V2 method, and `getMutationRequest` sets `insert_deduplication_token` from the same `QueryIdentifier.getDeduplicationToken`, so the body bytes and the token do not depend on the client. What was not compared is the client V1 wire path on `0.11.0`. For a client V1 connector with `exactlyOnce=true` the replay question is therefore open for this release; stopping it cleanly before the upgrade is the cautious choice, a precaution that this release did not measure.

### Rollback

The release workflow is meant to create the release and its tag at the merged commit and attach the archive; whether a publish-mode run of it does so is the open condition of `FORK-DELTA` item 22. Nothing in the data format changes, so a rollback is a code rollback. Tag `pre-v1.7.0_gg6` names commit `3a3a15a9`, the published tip of `custom_build` before this release, which is also tag `v1.7.0_gg5`. The tag is published together with this release.

1. Start from the published tip with nothing uncommitted. Run `git fetch --tags origin`, `git checkout custom_build` and `git merge --ff-only origin/custom_build`, and check that `git status --porcelain` prints nothing; a fresh checkout of the release tip lists nothing (measured). Set whatever it lists aside with `git stash -u`, keep it on its own branch, or work in a fresh clone, so that none of it becomes part of the rollback; do not commit it on `custom_build`, because step 2 branches from there and step 4 publishes that branch: the `git read-tree` of step 2 discards uncommitted and staged changes to tracked files without asking, and it overwrites untracked files at paths that the tag contains.
2. Restore the tree of the tag in one commit on a new branch, so that your local `custom_build` stays as published. This commit is `<rollback-commit>`:

```sh
git switch -c rollback-v1.7.0_gg6
git read-tree -u --reset pre-v1.7.0_gg6
git commit -m "Roll back v1.7.0_gg6"
git diff --quiet HEAD pre-v1.7.0_gg6 && echo ok
```

```text
ok
```

   After this step `git status` lists ` M gradlew.bat` without any change of yours: the tag's `gradlew.bat` has Windows line endings, and `.gitattributes` asks git to normalise `*.bat` files. While that line shows, `git switch` and `git revert` stop with "local changes would be overwritten". Run each of them with git's attributes switched off, as in `git --attr-source="$(git hash-object -t tree /dev/null)" revert <rollback-commit>` (git 2.40 or later); the forward path below does so. Measured on the dry run.

3. Redeploy the `v1.7.0_gg5` archive. If you kept the one you deployed before, use it. A GitHub release asset exists for `v1.7.0_gg5` (published 2026-10-28, SHA-256 `4c69b6fb3b22ab8f7c329383079cc284d3d2e0ae497f3ffb2f0114d171bc6767`). Otherwise check out tag `v1.7.0_gg5` in a clean worktree and run `./gradlew createConfluentArchive`. A rebuild from the tag is not byte-identical to that asset, although it has the asset's size; it compares equal to it entry by entry with `.github/scripts/compare_confluent_archives.py` (measured by the maintainers' rebuild). The `v1.7.0_gg5` archive carries client `0.9.6` and `lz4-java` `1.12.0`.
4. Publish the rollback commit. Where `custom_build` accepts pushes, run `git push origin rollback-v1.7.0_gg6:custom_build`, which does not depend on which branch is checked out. Where it requires a pull request, run `git push origin rollback-v1.7.0_gg6`, open the pull request into `custom_build` and merge it with a merge commit, so the rollback commit keeps its SHA for the forward path below. Until the rollback commit is on `origin/custom_build`, GitHub keeps running the `v1.7.0_gg6` workflows there.

Rehearsed on a dry-run merge of the release tip onto `3a3a15a9`: the block above, run unchanged, printed `ok`; after the rollback commit the branch has `VERSION` `v1.7.0_gg5`, has no copy of this note, and has a tree equal to tag `v1.7.0_gg5`, and `git revert <rollback-commit>`, run with git's attributes switched off as in step 2, restores the tree you rolled back from. To go forward again, once the rollback commit is on `origin/custom_build`, update your local branch with `git --attr-source="$(git hash-object -t tree /dev/null)" switch custom_build` and `git pull --ff-only`, run `git --attr-source="$(git hash-object -t tree /dev/null)" revert <rollback-commit>` on it, and publish the revert as in step 4: push it, or put it on a new branch and open a pull request where `custom_build` requires one. ## Known limits carried into this release

These limits exist in this release as they did before it; none is fixed here.

- `ClickHouseWriter.stop()` never closes its `ClickHouseHelperClient`, so every task start leaves at least one V2 client and its connection pool open for the life of the worker process. It matters on workers that restart or rebalance tasks often (read from the code: `ClickHouseWriter.stop`; that one is left per start, on both client lines, is `measured in research (not re-run)`). The count is higher than one per start in two cases, read from the code and not measured: with `exactlyOnce=true` the `KeeperStateProvider` constructor builds a second `ClickHouseHelperClient` that nothing closes, and a client V1 connector builds one more with every insert in `ClickHouseWriter.getMutationRequest`, which nothing closes either, so on client V1 the number of unclosed V2 client objects grows with the number of insert batches. Whether the connector releases those extra objects in some other way was not checked, so the note claims the count and that none of them is closed, not a measured leak.
- On client V2, the four-minute insert timeout (`clickhouseClientInsertTimeoutMs`, applied in `awaitInsertResponse`) has no effect while `async=false`, because the insert returns an already completed future, and the client's `socket_timeout` defaults to 0, so an insert can block on a stalled server (read from the code: `awaitInsertResponse` and the client timeout options; that it holds on both client lines is `measured in research (not re-run)`). A client V1 insert has no such timeout: `awaitInsertResponse` is called only from the three client V2 insert methods, and the three client V1 insert methods wait with `future.get()` and no timeout argument (read from the code: `ClickHouseWriter`), so `clickhouseClientInsertTimeoutMs` does not bound a client V1 insert. What the client V1 library does on a stalled server by its own timeout options was not examined, and nothing was measured for client V1.
- The documented limits of connectors under a rename (row B8): the Direct path (an unbuffered connector, `bufferCount` 0) with `reportInsertedOffsets=true` commits nothing under a rename (unless `exactlyOnce=false` and `ignorePartitionsWhenBatching=true`), a many-to-one rename shares one state record, exactly-once buffering is claimed only for a rename that maps each source topic to its own target and was not probed under an SMT that changes the partition, and the state-removal call for a revoked partition removes nothing under a rename.
- The two retriable `DataException` behaviours of row C3 are not asserted by any test, and a decision on changing them is open.
