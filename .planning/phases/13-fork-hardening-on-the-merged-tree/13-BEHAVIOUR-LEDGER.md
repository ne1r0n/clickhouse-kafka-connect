# Phase 13 Behaviour Ledger

**Purpose:** one place that lists every operator-visible behaviour change made in Phase 13 (Fork Hardening on the Merged Tree), so that Phase 15 can write the `CHANGELOG.md` section, the `docs/FORK-DELTA.md` rows and the operator rollout checklist (ROLL-01) from it. Phase 13 itself writes no CHANGELOG or FORK-DELTA prose (CONTEXT phase boundary).

**Source plans:** 13-01 (L-01..L-07), 13-02 (L-08), 13-03 (L-09..L-13), 13-04 (L-14, L-15), 13-05 (L-16..L-18), 13-07 (L-19). Plan 13-06 is test-only and recorded "no behaviour change". Phase 13 recorded no entry beyond L-19. Phase 15 appended L-20..L-22 (2026-10, plans 15-01 and 15-03); they are marked with their Phase 15 source plan in the table.

**How to read it:** the entries were copied from each plan's `## Behaviour ledger` section and reduced to one row each. The wording of the behaviour is the plan's; the columns after it add the decision IDs from `13-CONTEXT.md`, the pinning test, whether an operator can observe the change, and where Phase 15 should put it. Test references are `Class#method` unless a whole class pins the entry. The ledger holds test names, decision IDs and message formats only: no record data, credentials or connection strings.

**Destination key:** CHANGELOG = the `1.7.0_gg1` section of `CHANGELOG.md` (PUB-01); FORK-DELTA = a row in "What this fork still patches", or an item in "Known costs and open items" (PUB-02); ROLL-01 = an item in the operator rollout checklist.

## R-01 backfill procedure

Source: L-01, decision D-08. Phase 15 copies this into the rollout checklist (ROLL-01) as written.

Before this change, on the metadata-free route (`insertFormat=json` set explicitly), a `Struct` record or a Debezium-envelope record was routed to RowBinary against a synthetic column-less table. The insert ran, the connector marked the offset range AFTER_PROCESSING, and no row was stored.

With exactly-once on (`exactlyOnce=true`, state in ClickHouse Keeper through the KeeperMap table), a range marked AFTER_PROCESSING is treated as delivered, and a replay of that range is dropped as already inserted. So installing the fix alone does not recover the lost data. Recovering it needs both steps, in this order:

1. Stop the connector, then reset the consumer group offsets of the affected topic-partitions to the position from which data must be recovered.
2. Clear the KeeperMap state rows for those topic-partitions. Skipping this step makes the connector see the replayed ranges as already stored (state AFTER_PROCESSING) and drop them.

Then start the connector. Operator fact 2 (recorded in CONTEXT) says no live pipeline is known to use this route, so this applies only to a pipeline that did. The change is one-way: reverting it brings back the silent loss.

## Nested-null semantics by route

Source: L-07, L-08, L-09, L-10, L-11, L-12, decisions D-09, D-10, D-11, D-16. Phase 15 needs this split verbatim in FORK-DELTA so the next sync sees the reasoning.

**RowBinary route (default for Avro/Protobuf/Struct records):**

- A nested null *container* (Array or Map) in a non-nullable slot is coerced to an empty container, whatever the table's DEFAULT columns are (D-09, L-09). This mirrors upstream #820's top-level rule.
- A nested null in a non-nullable scalar slot, or in a Tuple slot or field, throws `DataException` (WRT-08, L-10). TUPLE slots follow `Column`'s reported nullability (D-10, D-16, L-11): because `Column.extractColumn` drops Tuple and Enum nullability, a DESCRIBE-derived Tuple or Enum slot counts as non-nullable and a null in it throws (L-11, L-13).
- Nullable slots keep their null marker; Variant slots keep discriminator 255.
- The top level is unchanged (D-11, L-12): a null in a non-nullable scalar or Tuple column keeps upstream's `RuntimeException("An attempt to write null into not nullable column '<name>'")`, and a null in a non-nullable Array or Map column reads back `[]` or `{}`.
- Through `put()`, the nested `DataException` is the root cause of a `RuntimeException`: `Processing.doInsert` wraps every failure in `RuntimeException(queryId, e)`, and `Utils.handleException` wraps again in `RuntimeException("Number of records: N", e)`. It is never a bare `DataException` from `put()`, so callers and tests must walk the cause chain.
- The whole batch fails, with no row written. With `errors.tolerance=none` the task fails and fails again on every retry of the same batch; with `errors.tolerance=all` the whole batch goes to the DLQ. Per-record isolation is out of scope because it would change batch composition, which the exactly-once invariant forbids.

**Metadata-free JSON route (L-07, L-08):**

- Nested nulls are sent as explicit JSON null and ClickHouse coerces them to the element default in non-nullable slots (`Array(Int32)` `[1, null]` stores `[1,0]`; `Map(String,String)` `{k: null}` stores `{'k':''}`). Nullable slots keep NULL.
- Top-level null fields are omitted, so Nullable columns store NULL and non-nullable columns take their DEFAULT or type default.
- This relies on the server's default `input_format_null_as_default=1` (L-08).

The result is a deliberate cross-route asymmetry: the same producer data that stops a task on the RowBinary route is coerced to defaults on the JSON route.

## TYPE-08 message change

Source: L-15. For a non-nullable, no-default `Int256` or `UInt256` root column, `validateDataSchema` now throws the same actionable `DataException` that DYNAMIC and UNKNOWN columns get (column name, type, and the two escape hatches `insertFormat=json` and `bypassRowBinary=true`, never the field value), where it previously reported only "Data schema validation failed." Nullable or defaulted columns and `bypassSchemaValidation=true` runs reach the same message later, from `doWriteColValue`'s default branch. `Int128` and `UInt128` are unaffected and round-trip their INT64 extremes.

## Known JSON-route gaps

Source: L-02, L-03, L-04, L-05, L-08. These are known and recorded, not fixed in Phase 13. Phase 15 lists them in FORK-DELTA and in the JSON-route type notes of the rollout checklist.

- **D-05, the upstream route (L-03).** `bypassRowBinary=true` without an explicit `insertFormat=json` keeps Jackson's defaults: `java.util.Date` is written as epoch milliseconds (ClickHouse reads it as seconds) and `byte[]` as base64. The conversion of Phase 13 applies only on the metadata-free route, so upstream's bytes stay identical. A fix could go upstream as a PR later.
- **D-17, Date into DateTime (L-04).** On the metadata-free route a Kafka `Date` is an integer day count, so a `Date` field written to a `DateTime` or `DateTime64` column lands the days as seconds (a 1970 timestamp). `Date` into `Date` and `Date32` is at parity.
- **D-18, `io.debezium.time.Timestamp` (L-05).** The CDC conversion handles only Connect `Timestamp`, `io.debezium.time.Date` and `io.debezium.time.MicroTimestamp`. A raw `io.debezium.time.Timestamp` millisecond long passes through and is read as seconds; `ZonedTimestamp` strings pass through unchanged. *Phase 15 note (2026-10): L-20 closes the `io.debezium.time.Timestamp` millisecond gap and also converts `NanoTimestamp`; only `ZonedTimestamp` strings still pass through unchanged.*
- **ByteBuffer asymmetry (L-02).** On the metadata-free route a `ByteBuffer` writes its remaining bytes; RowBinary's `Struct.getBytes` writes the whole backing array. They differ when position is not zero or limit is not capacity. Not reconciled, because RowBinary is upstream code.
- **Non-nullable null coercion setting (L-08).** The JSON-route null outcomes for non-nullable columns depend on the server's `input_format_null_as_default` staying at its default of 1.
