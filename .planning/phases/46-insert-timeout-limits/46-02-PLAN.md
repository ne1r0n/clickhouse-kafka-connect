Purpose: ROADMAP Phase 46 criteria 2 and 3 for the write-side stall on client V2 (TMO-03), and criterion 1's recorded side (TMO-02, U-1), scoped to what is pinned: once the body has been sent, a progress-streaming response keeps its recorded behaviour; while the body is still being sent, the deadline applies even if the server already streams progress.

Decisions taken in this plan (Claude's discretion): serialization time counts against the deadline, because the writer's `DataStreamWriter` serializes records and writes them to the socket in one pass, so separating them would need per-write work on the insert hot path (AGENTS.md); the time spent serializing already counts against `max.poll.interval.ms`, which this setting protects. The watchdog is one lazily created daemon thread per writer, shut down in `stop()`, so a slow cancel on one task never delays another task's deadline and no static state is added. The orchestrator decided (plan-check B1) that the deadline is a private static nested class of `ClickHouseWriter`, so it is pinned through the writer and its queue behaviour by a throwaway probe and an anchor row rather than by a unit test of the class.

Rollout consequence this plan creates (stated in plans 46-04 and 46-05): a V2 insert whose body, serialization included, is still being sent when `clickhouseClientInsertTimeoutMs` elapses now fails and is retried, even when the upload is progressing and even when the server already streams progress; the server may keep what it received.

Output: one code-and-test commit, evidence E-04..E-06. Nothing is pushed.
</objective>
