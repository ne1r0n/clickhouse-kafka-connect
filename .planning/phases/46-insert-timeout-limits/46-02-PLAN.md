Bound the client V2 write-side stall: a server that stops reading the request body today blocks the SinkTask thread for good (research: blocked > 20 s with a 500 ms per-insert `socket_timeout`; the per-insert option bounds reads only).

1. Tracer (Task 1). Write the V2 pins and run them red on the unchanged production tree (a worktree at R0). Record E-04.

3. Task 3. Four worktree mutations, cache-busted testUnit, anchors and the tail gate. Record E-06.

Purpose: ROADMAP Phase 46 criteria 2 and 3 for the write-side stall on client V2 (TMO-03), and criterion 1's recorded-limit side (TMO-02, U-1): the deadline is disarmed once the body is sent, so a progress-streaming insert keeps its recorded behaviour, pinned here.

Decision taken in this plan (Claude's discretion, research Open Question 1): serialization time counts against the deadline. The writer's `DataStreamWriter` serializes records and writes them to the socket in one pass, so the two cannot be separated without per-write work on the insert hot path (AGENTS.md); the time spent serializing already counts against `max.poll.interval.ms`, which this setting protects; and with the 4-minute default only a batch that takes minutes to serialize and send is affected, which the help text (plan 46-05) and FORK-DELTA (plan 46-04) state. The watchdog is one lazily created daemon thread per writer, shut down in `stop()`, so a slow cancel on one task never delays another task's deadline and no static state is added.

Rollout consequence this plan creates (stated in plans 46-04 and 46-05): a V2 insert whose body, serialization included, is still being sent when `clickhouseClientInsertTimeoutMs` elapses now fails and is retried, even when the upload is progressing (pinned by the slow-upload case); the server may keep what it received.

Output: one code-and-test commit, evidence E-04..E-06. Nothing is pushed.
