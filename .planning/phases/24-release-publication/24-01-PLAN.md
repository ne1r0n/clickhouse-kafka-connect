## Conditional checkpoint (D-04 branch 3)

`autonomous: true` covers D-04's branches 1 and 2, the outcomes research R2.2 expects under D-14's Connect-typed matrix. Branch 3 is a planned stop, not a planned task. It fires only when Task 2's run shows a Map value sentinel or any record content beyond the key, and it is skipped otherwise.

When it fires:
1. The executor stops Task 2 at step 3. It commits nothing of Task 2 and leaves the test file uncommitted in the working tree. Task 1's commits stay.
2. It returns `## CHECKPOINT REACHED` with **Type:** `decision`, **Gate:** `blocking-human`, **Plan:** `24-01`, **Progress:** 1/3, and Task 2 as the current task, status "awaiting decision".
3. Under Checkpoint Details it puts the captured text, which holds sentinels only; the five-destination table (key yes/no, value yes/no) as measured; the server version; and the D-14 scope note.
4. Under Awaiting it asks for the user's route. The plan proposes none, and any route other than hold is carried out by a planning run, never by this executor:
   - a fix, planned through `/gsd-plan-phase 24` ("Add more plans"). This is a `src/main` change outside D-06's lean scope, so it happens only on the user's say-so.
   - disclose as measured: the user accepts the residual as measured, and a planning run revises this task's assertions and plans 24-03 and 24-04's wording to the measured text.
   - hold the phase.

The orchestrator presents the checkpoint to the user. A `blocking-human` gate is never auto-approved or auto-selected, and it needs the user's own answer given directly to the orchestrator; a relayed answer is refused. Task 3 and plan 24-02 do not start until the answer is in. The SUMMARY records the checkpoint and the verbatim answer.
