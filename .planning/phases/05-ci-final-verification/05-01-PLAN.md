## Decisions this plan makes explicitly

Three questions were left open by the research and pattern passes. Each is resolved here with its
reason, rather than left for the executor to improvise.

### DEC-A - The coverage parser is a separate checked-in file, not an inline heredoc

`.github/scripts/jacoco_summary.py` is a real file in the repo; the workflow invokes it by path.
CONTEXT.md and RESEARCH.md both frame this phase as touching "exactly one file", which argued for
inlining the parser inside the workflow's `run:` block. Rejected, for four reasons:

1. **It is testable verbatim before it ships.** Task 1's gate runs the exact artifact CI will run,
   against this repo's real JaCoCo XML. A heredoc can only be tested by extracting it - that is
   testing a copy, and the copy is not what the runner executes.
2. **Quoting hazard.** The parser contains dollar signs, braces, backslashes and f-strings, every one
   of which is a shell-and-YAML interpolation trap inside a block scalar. That class of bug only
   manifests on the runner, which is the most expensive place to discover it.
3. **D-06 is satisfied exactly.** D-06's locked contrast is with a *marketplace action* and with a
   *Gradle task*. A repo-local script invoked from `run:` is neither; it introduces no third-party
   supply-chain dependency and touches no build logic.
4. **It is strictly better for rebasability.** `.github/scripts/` is a path upstream has no file at,
   so it can never produce a merge conflict on a future upstream sync - unlike growing `tests.yaml`,
   the one file D-01 already accepts a conflict on.

This is a departure from CONTEXT.md's "exactly one file" *phrasing*, which is scope framing (no
`src/`, no `build.gradle.kts`, no test changes) rather than a locked decision. Recorded here so the
departure is visible rather than silent.

### DEC-B - The script writes both destinations itself; the workflow step carries no pipe

D-12 locks "the coverage markdown is written to both `$GITHUB_STEP_SUMMARY` and stdout".
RESEARCH.md's skeleton implements that by piping the script's stdout into a `tee -a` of the summary
file. The decision is honored exactly; the plumbing is not.

GitHub Actions' default `run:` shell on Linux is `bash -e {0}` - it does **not** set `pipefail` (only
an explicit `shell: bash` does). Under a pipe, the step's exit status is the last command's, so a
crashed parser would report success. That failure mode lands precisely on D-08's always-run path -
the red-test-run case where the summary crashing is most likely and most worth knowing about. Having
the script open `GITHUB_STEP_SUMMARY` and append to it removes the pipe, makes the step's exit status
the script's own unconditionally, and makes the local gate exercise byte-for-byte the code path CI
runs.

### DEC-C - `actions/upload-artifact@v4` (resolves RESEARCH.md Open Question #2)

Live-verified this planning session: `v4` resolves to commit
`ea165f8d65b6e75b540449e92b4886f43607fa02`. CI-01 does not name this action, so the only binding
constraint is criterion 1's "no deprecated actions left" - and v4 is explicitly not deprecated: the
action's own README banner deprecates v1/v2/v3 only and directs readers to v4. v4 is also the tag
RESEARCH.md's verified skeleton and PATTERNS.md's target shape both carry, so choosing it keeps the
workflow identical to the evidence base this phase was researched against.

`v5`, `v6` and `v7` were also confirmed to resolve, and `v7.0.1` is the current latest release. v7
keeps all three inputs used here (`name`, `path`, `retention-days`), so a later bump is a one-line,
zero-risk follow-up. Surfaced under Flagged Assumptions rather than silently absorbed.
