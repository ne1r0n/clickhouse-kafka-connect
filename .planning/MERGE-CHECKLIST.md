# Merge Resolution Checklist — `v1.6.0_gg1-sync`

This document is the checked-in, per-path resolution gate for the `custom_build` → `v1.6.0` merge (Phase 6, `sync/v1.6.0`, merge commit `673d29c3d5dc24b97de3b022acdfe473e1a5493c`). It turns the merge's conflict surface into a living record: **Phases 7 through 10 each own a subset of Section 1's rows and flip their own rows from `pending` to `done` inside their own commits.** **Phase 11 asserts zero `pending` rows remain before `custom_build` is published** — that assertion is what makes this a gate rather than a document. Do not flip a row you do not own; do not resolve, re-express or edit any conflicted source file from this checklist alone — the row records intent, the owning phase's plan executes it.

Section 1 is generated from `.planning/scripts/conflicted-paths.txt` (the committed output of `git merge-tree --write-tree --name-only -z custom_build v1.6.0`), never hand-transcribed from research prose. Section 2 lists paths that merge with **no conflict marker at all** yet carry fork logic a conflict-only reviewer would miss. `## Recorded Facts` closes the phase's open version and production-config questions.

## Recorded Facts

Production runs the shaded jar built from this repository, so the resolved version *is* the production version — no separate runtime verification is needed. This satisfies SYNC-04's requirement to record the resolved version, not the catalog literal (D-11).

2. **The other three D-12 resolved facts — `repo-derived`.** Also confirmed against the resolved `dependencies` graph in plan 06-02, each a fork-only build decision that a wholesale catalog adoption would otherwise have silently erased:
   - `org.apache.kafka:connect-api` resolves to **`4.1.1`** (upstream's catalog declares `2.7.0`) — the fork's override, carrying the LZ4 `resolutionStrategy` coupling with it.
   - `org.slf4j:slf4j-reload4j` resolves to **`2.0.17`** — upstream's catalog has **no entry at all** for this coordinate; it survives only because it is kept as a literal inline dependency in `build.gradle.kts` per D-16.
   - The `org.lz4:lz4-java` capability conflict resolves via `at.yawk.lz4:lz4-java:1.10.2` (BLD-06) — absent from both `main` and `v1.6.0`'s catalogs, coupled to the Kafka `4.1.1` override.

3. **Production-config audit, both halves closed, no operator follow-up outstanding (SYNC-05, D-10).**
   - **Buffered-delivery half (`bufferCount>0` + `exactlyOnce=true`) — `repo-derived`.** `bufferCount` does not exist in the pre-merge fork (`custom_build:src/main/.../ClickHouseSinkConfig.java`, grepped for `bufferCount`/`BUFFER_COUNT`: zero matches) — it is new in `v1.6.0` (`ClickHouseSinkConfig.java:56`: `public static final String BUFFER_COUNT = "bufferCount";`, `:85`: default `0`). No pre-merge connector config can set a key that did not exist, so upstream's new startup rejection (thrown unless `bufferFlushTime=0` and `ignorePartitionsWhenBatching=false`) is structurally unreachable on upgrade.
   - **Topic-split half (`enableDbTopicSplit=true` + `exactlyOnce=true`) — `operator-confirmed`.** Both `EXACTLY_ONCE` (`ClickHouseSinkConfig.java:33`) and `ENABLE_DB_TOPIC_SPLIT` (`:47`) exist today and both default to `false`. The operator confirmed on 2026-09-18 that the topic-split functionality is not used in production. The repository can show the flags exist and default `false`, but it cannot show what a deployed connector's props map actually sets — which is exactly why this half needed a human answer rather than a repo-derived one. No operator follow-up remains on either half.
