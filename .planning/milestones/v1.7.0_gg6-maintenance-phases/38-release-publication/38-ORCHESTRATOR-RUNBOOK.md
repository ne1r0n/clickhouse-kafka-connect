# Phase 38: orchestrator runbook for the publication of v1.7.0_gg6

For the orchestrator only. The user is the only one who pushes, tags or dispatches, with their own account, from the four handoff files. The orchestrator never acts on an approval relayed by another agent: only the user's own message to the orchestrator counts, and it is recorded verbatim with who received it. The orchestrator reads GitHub with read-only calls (`git ls-remote`, `gh auth status`, `gh api` without a write flag, `curl` GET) and runs no push, tag, dispatch, re-run, cancel, comment, merge or close. This runbook is the orchestrator-inline half of the publication: the approval gates, the build of the merge commit M, the readings after the user's steps, the record that closes the earlier caveat about the publish path, and the contingencies.

## Contingencies

- **C-1. `custom_build` moved** (at any pre-check): nothing was pushed or the approval is void. The orchestrator merges `origin/custom_build` into `sync/v1.7.0` (never a rebase), checks the landed lines against the anchors (`fork-anchors.txt`; a Dependabot merge can break the fork-anchors invariant), re-gates (allow-list compare, Docker-free `testUnit`, the two merge gates, the suites if `src` or `build` changed), rebuilds M if needed and asks the user whether to absorb or hold. The user's approval must be asked again.
- **C-2. A CI-only defect on the runner** (a failure before the compare step): no re-dispatch; a gap for Phase 37 (Phase 38 cannot edit `.github/`); the user decides whether to authorise a `.github/` exception.
- **C-3. The compare reports `UNALLOWED` or `STALE-ROW` on the runner**: investigate against the artifact; the allow-list is derived from local builds; no edit of `.github/`; a corrected list needs a new local gate and a new review of what changed.
- **C-4. A red `tests.yaml` run on X0 or M** (or not exactly one run on M): stop; no dispatch; report; for M the way back is the note's forward-only rollback, never a force-push.
- **C-5. An accidental publish from the wrong ref**: a dry run is harmless; a publish that was not meant is the user's to delete (release and tag), after the orchestrator has read the state.
- **C-6. A failed publish run**: read the state with read-only calls (release, tag ref, draft); the user chooses between deleting the release and the tag and dispatching once more, or a manual release (the earlier caveat then stays open).
- **C-7. The date mismatch**: the CHANGELOG heading date differs from the UTC date of the merge: ask the user directly, as in O2.
- **C-8. A hand-pushed `v1.7.0_gg6`**: the tag gate refuses to publish; the user deletes that tag and nothing else; the orchestrator re-reads `git ls-remote --tags origin 'v1.7.0_gg6*'` before the publish handoff goes ahead again.
