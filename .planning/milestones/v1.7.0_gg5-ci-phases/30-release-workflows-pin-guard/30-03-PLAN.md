## Execution environment

As in 30-01-PLAN.md "Execution environment" (zsh traps, read-only network rules, evidence format). Specific to this plan:

- **Who runs what.** A dispatched `gsd-executor` runs Task 1 and returns Task 2's checkpoint. The user answers the orchestrator directly and dispatches on GitHub. The orchestrator, holding those answers, runs Task 3 **inline**. Executors refuse relayed approvals (Phase 11 lesson, Phase 17 D-11 and Phase 29 practice), so this plan never asks an executor to act on one.
- **The one-way door.** Pushing publishes the local `.planning` tail (136 files changed since `v1.7.0_gg4` at planning time) and the Phase 30 commits to the public fork, and deleting the branch afterwards does not unpublish them. Task 2 is the `checkpoint:decision` before it. Under option `self` the user pushes. Under option `push` the orchestrator runs exactly the named command in Task 3 step 1, and nothing else. No agent pushes on its own judgement.
- **Why the scratch branch can only dry-run.** `workflow_dispatch` runs the selected ref's copy of the file. On `sync/v1.7.0`, `github.ref != 'refs/heads/custom_build'` holds, so the dry steps run and `Publish release` is skipped, even if the form does not show the `dry_run` box (research Pitfall 3, A3).
- **The hazard.** On `custom_build` the files are still upstream's. A dispatch there would run `actions/create-release` for the existing tag `v1.7.0_gg4`, which publishes a real release on it. The checkpoint therefore puts the branch selection first, and Task 3's release-list comparison detects such a release.
- **GitHub REST**, unauthenticated: read `/rate_limit` first and stop below 20 remaining. A body without the expected array or object is an error, never a result. The annotations of a job are at `/repos/ne1r0n/clickhouse-kafka-connect/check-runs/<job id>/annotations`. At planning time, javac warnings appear there as warning annotations with an empty title, so checks select by title. The published-release list is `/releases?per_page=100`; drafts are invisible without a token, which is why the user's own Releases-page check and the workflow's `Dry run cleaned up` notice are part of the proof.
- **Files.** Snapshots and REST bodies go in `/tmp/gsd30/exec/dry/`: `origin-tags-before.txt`, `origin-heads-before.txt`, `releases-before.json`, `tracer-runs.json`, `tracer-jobs.json`, `tracer-ann.json`, `pushed-sha.txt`, then `runs-T.json`, `jobs-pre-release.json`, `jobs-release.json`, `ann-pre-release.json`, `ann-release.json`, `origin-tags-after.txt`, `origin-heads-after.txt`, `releases-after.json`. If `/tmp` was cleared between tasks, rebuild the before-files from E-08's text blocks.
- **A red or wrong run** is not re-run, re-dispatched or fixed on the spot. Attribute it first: read the failing step from `/jobs` and its annotations. If the cause is a workflow defect, the fix is a `.github/` edit, planned with `/gsd-plan-phase 30 --gaps` and followed by a new approved push and new dispatches. Raise a `checkpoint:decision` with gate `blocking-human` that offers that route or hold.
