<objective>
Pin `jsonInsertColumns` exactly as it behaves today — the parsing contract (COLS-01) and every
insert-time consequence of the column list: the default empty list (COLS-02), an explicit subset
against non-trivial DEFAULTs (COLS-03), extra payload keys (COLS-04), a nonexistent column and its
error classification (COLS-05), and the non-explicit path's surprising interaction with
`cleanupExtraFields` (COLS-06).

Purpose: `jsonInsertColumns` is reachable only through `doInsertJsonV2`'s 5-arg
`client.insert(table, columns, ...)` overload. The two pre-existing explicit-JSON tests use String
records, which take the 4-arg overload with no column list, so this feature ships in production
with zero behavioral coverage today.

Output: one new Docker-free parsing test class and one new ClickHouse-backed insert test class,
plus a recorded observation of the exact exception class and ClickHouse error code COLS-05 surfaces.
</objective>

<assumption_delta_decision>
## Assumption delta — the `pluralization` signal on `jsonInsertColumns` routes

**Signal:** "the list also applies on the non-explicit JSON path" (COLS-06). What was written about
as one thing — "the JSON insert path" — is now at least two, and there is a third route that
behaves differently.

**The noun that is now primary:** not "the JSON insert path" but **the insert route**, of which
this connector has three, distinguished by which `client.insert` overload they call:

| Route | Entry | `client.insert` overload | Honours `jsonInsertColumns` |
|---|---|---|---|
| explicit metadata-free JSON | `insertFormat=json` + SCHEMA_LESS records | 5-arg, with the column list | yes |
| non-explicit JSON | `insertFormat` unset + SCHEMA_LESS records | 5-arg, with the column list | yes |
| String | STRING_SCHEMA records | 4-arg, no column list | **no** |

**Decision: `add-alongside`.** The tests name the route explicitly instead of saying "the JSON
insert path": COLS-02..05 are labelled and commented as the explicit metadata-free route, COLS-06
is labelled and commented as the non-explicit route, and the class Javadoc states in one sentence
that the String route takes the 4-arg overload and therefore never sees the column list at all.

**Rationale:** promoting the identity — making every insert route that accepts a column list honour
`jsonInsertColumns` identically — would mean changing `doInsertStringV2` in main code. CONTEXT.md
D-01 names that change explicitly as an escalation, and CONTEXT.md Deferred Ideas already records
the asymmetry as surfaced-but-not-fixed. Naming both JSON routes alongside each other is the
largest generalization available without a main-code change.

**Accepted debt:** the String route's silent disregard of `jsonInsertColumns` stays unpinned and
unfixed. An operator combining `insertFormat=json`, a `StringConverter` and a column list gets no
error and no column clause.

**What would force a later promote:** a decision to pin or fix the String route. At that point
"every insert route that accepts a column list honours `jsonInsertColumns` identically" becomes a
single invariant test across all three routes, and the primary noun promotes from "the JSON insert
route" to "the insert route". A test encoding that invariant *today* would necessarily pin the
asymmetry rather than the intent, so it is suggested and not written.
</assumption_delta_decision>
