## Decisions this plan makes explicitly

### DEC-D - How CI-03's job-summary sub-claim is verified (resolves RESEARCH.md Open Question #1)

RESEARCH.md falsified D-12's stated premise: unauthenticated `GET .../actions/jobs/{id}/logs` and
`.../runs/{id}/logs` return 403 "Must have admin rights to Repository", and
`.../artifacts/{id}/zip` returns 401. So the rendered summary text cannot be re-fetched by teeing it
into a job log. The research handed the planner three options and asked for an explicit choice.

**This planning session found a fourth, better route, and live-verified it.** The run-jobs endpoint
returns each job's `steps[]` array with per-step `name`, `status` and `conclusion`, and that array
**is populated unauthenticated for recent public runs**. Proven against this fork's own upstream
sibling: `GET /repos/ClickHouse/clickhouse-kafka-connect/actions/runs/34991824280/jobs` returned 14
named steps with conclusions, no token. The reason RESEARCH.md saw an empty array on the target repo
is that the only historical run there is from 2026-01-29 - roughly eight months old, past GitHub's
~90-day step and log retention. A run created by this plan is minutes old, so its steps are present.

CI-03's summary sub-claim is therefore decomposed into three parts, two of them machine-verified:

1. **Content correctness - machine-verified locally, pre-push, deterministic.** Task 1 runs the
   workflow's exact `Generate coverage summary` command against the freshly regenerated JaCoCo
   reports with `GITHUB_STEP_SUMMARY` pointed at a temp file, and asserts the headline rows and all
   15 fork-class rows appear in both that file and stdout. Same script, same code path, same inputs
   CI has. (Proven working against this repo's real reports during planning.)
2. **That it ran in CI and exited 0 - machine-verified unauthenticated.** Task 3 asserts the step
   named exactly `Generate coverage summary` carries `conclusion: success` in the run's job step
   list, and that the step named `Run tests` does too, so the summary provably came from a real test
   execution rather than a skipped step.
3. **That GitHub rendered it in the run's Summary tab - one scoped human glance.** This is GitHub
   platform behavior, not this fork's code, and there is no unauthenticated endpoint for it. It is a
   single `<verify><human-check>` on Task 3, harvested into UAT at end of phase per
   `workflow.human_verify_mode = end-of-phase`.

Explicitly not used: any `/logs` or `/zip` endpoint, and no personal access token is minted. D-11's
"no `gh` install, unauthenticated `curl` only" posture is preserved intact rather than quietly
relaxed.

### DEC-E - Red-CI-run policy (CONTEXT.md left this to discretion; recorded, not improvised)

- A failure rooted in the **workflow configuration** - a bad action input, a wrong artifact path, a
  runner-environment mismatch, a Testcontainers setup problem on the runner - is fixed in
  `.github/workflows/tests.yaml` or `.github/scripts/jacoco_summary.py` and re-pushed inside this
  plan. That is this phase's own job, which is why those two files appear in `files_modified`.
- A failure exposing a **test or product** problem that does not reproduce locally does NOT get
  chased with speculative CI pushes. Stop, record the finding, and route it to PROJECT.md's `Active`
  follow-up list for its own plan. Two of the four existing `Active` items were found exactly this
  way; absorbing a new one silently into a "CI fix" is how they become invisible.
- Either way, the prohibitions above bind: nothing is disabled, filtered, or scoped down to turn the
  badge green.

### DEC-F - Run location and poll cadence (CONTEXT.md discretion items)

Locate the run by `head_sha` of the pushed commit, filtered further to `path` equal to
`.github/workflows/tests.yaml`, and assert exactly one match. "Most recent run on the branch" is
rejected: it silently attributes another commit's result to this work if any push races it.
`head_sha` filtering and the `path` field were both confirmed present on the unauthenticated run
listing this session.

Poll no tighter than once per 60 seconds, with a give-up window of 60 minutes (the job's own
`timeout-minutes: 45` plus queueing headroom). The unauthenticated budget is 60 requests per hour -
confirmed via the `x-ratelimit-limit` header on every response captured during research - so a
60-second cadence over 45 minutes spends ~45 requests and leaves headroom for the jobs and artifacts
calls that follow.

### No tracer task in this plan

TRACER_MODE is on and the phase's tracer is 05-01 Task 1, which this plan depends on. 05-02 creates
no artifact and modifies no layer on its happy path - it runs an existing suite, pushes an existing
branch, and reads an API. A second tracer here would have nothing to wire end-to-end.
